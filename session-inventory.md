# Inwentaryzacja DSH przed przenośnym importem sesji (N004)

Stan źródeł: submoduł `deepseek-harness` w chwili wykonania N004. Ten dokument opisuje istniejące punkty wejścia, nie projektuje nowego formatu. Decyzje docelowe są w [plan.md](plan.md).

| Obszar | Obecny właściciel i API | Znaczenie dla importu |
| --- | --- | --- |
| Session | `packages/core/session`: `ctx.sessions.create/get/fork/flush`, `session.append`, `snapshotEvents`, `deriveMessages`; trwała historia jest append-only, a model-visible surface jest projekcją. | Import tworzy nową sesję i zdarzenia/projekcję; nie przepisuje istniejącego logu ani nie odgrywa działań. `flush()` jest istniejącą barierą trwałości. |
| Agent | `packages/core/agent`: `ctx.agents.create/resume`, `AgentFactory`, `AgentDriverFactory`/`AgentDriverSelector`; lifecycle, publikacja i teardown należą do `agent-loop`. `AgentDriver` ma dziś tylko `start` i `dispose`. | Dodać obowiązkowe porty eksportu/importu każdemu pełnemu driverowi. Identyfikator drivera musi być odrębny od provider/model i zapisany trwale. |
| Standardowy loop | `packages/core/agent-loop`: tworzy/wznawia agenta i składa żądania z logu sesji. | Jego kontekst można eksportować z kanonicznych wiadomości oraz zdarzeń; port importu ma odtworzyć model-visible historię bez uruchamiania starego turnu. |
| Codex | `packages/core/agent-codex`: alternatywny driver app-servera, binding `codex/thread-bound`, eventy `codex/turn-bound`, `codex/item/*`, `codex/usage`, `codex/error`; bramka modelowa w `model-gateway.ts`. | DSH dziś projektuje fakty, ale kolejne żądanie bazuje na prywatnym threadzie Codexa. Sam log DSH nie wystarcza do wiernego wznowienia po usunięciu `CODEX_HOME`. |
| Tools | `packages/core/tools`: `ctx.tools.schemas(scope)`, `get`, rejestracja, `tools/pre-execute` → guard → `tools/execute` → `tools/post-execute` → `tools/result`. | Port Codexa powinien wywoływać ten sam executor/policy i zapisywać tool call/result, bez natywnej ścieżki wykonania. |
| LLM | `packages/llm/llm`: `ctx.llm.stream`, rejestr adapterów, katalog provider/model, wspólny format message/content/stream; `llm-retry` jest osobnym właścicielem retry. | Obecna bramka Codexa konwertuje Responses na Chat Completions albo proxyuje Responses, lecz nie utrwala pełnego oryginalnego i wysłanego payloadu z korelacją DSH. |
| Settings | `packages/settings/settings` + `settings-file`: przestrzenie nazw, `get/watch/update/replace/mutate`, rewizje i `describe({ redactSecrets: true })`; `packages/api/settings-controller` wystawia edycję i credentials. | `codex` ma osobną przestrzeń. GUI modeli musi edytować ją przez istniejący mechanizm rewizji i redakcji sekretów, nie kopiować wartości credential do archiwum. |
| Session Remote | `packages/api/session-controller`: `list/search/create/selectModel/modelCatalog/rename/fork/prompt/attachment/updateQueue/cancel/page` i strumienie; katalog łączy trasy LLM z katalogami driverów. | Brak operacji podglądu i zatwierdzenia importu; trzeba dodać jawne tworzenie nowej sesji z wybranym driverem i lineage. |
| Export | `packages/session-query/session-log-export`: komenda `/export`, uwierzytelniona trasa `/api/session.export`; strumieniowany ZIP przez `fflate`, `session[.vN].jsonl` dla korzenia, logi potomków w `subagents/`, referencjonowane obrazy w `media/` i pliki w `files/`. Żywy log jest flushowany przed odczytem. | ZIP dziś nie ma manifestu, prywatnego stanu drivera ani importera. Bariera jest per-log, nie wspólnym punktem spójności całej sesji, potomków i artefaktów. |

## Zgodność starych danych

Aktualny logiczny format Session to v2 (`SESSION_FORMAT_VERSION = 2`). Statyczny `session-format-catalog` zawiera czytniki fizycznych v0, v1, v2 i sąsiednie migracje v0→v1→v2. Migracje są walidowane i nie oznaczają prawa do zmiany, nadpisania lub usunięcia raz opublikowanych generacji JSONL. Nowy format archiwum musi zachować te generacje i dodać własny wersjonowany manifest/artefakty; nie wolno reinterpretować starego ZIP jako kompletnego checkpointu drivera. Stary ZIP może dać tylko jawny import historii/transcriptu, jeśli walidacja potwierdzi kompletność danych potrzebnych do takiego poziomu; w przeciwnym razie odmowa. Nie deklarować wiernego `Codex → Codex` ani odtworzenia workspace na podstawie samego starego archiwum.
